# ARA 3.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make ARA's scan complete and honest about failures, and have every scan write a self-contained HTML report next to the JSON.

**Architecture:** One executable file `ara`, object-oriented: an HTTP client with retry and pagination, collectors that list role assignments and PIM instances once per subscription and management group, a builder that merges them into `RoleAssignment` rows, a scanner that drives the loop and records failures, a resolver for principal names, and one output handler per format. Tests live in one file and use fakes instead of the network.

**Tech Stack:** Python 3.7+ standard library only (`urllib`, `json`, `csv`, `argparse`, `unittest`). The report is plain HTML, CSS and JavaScript held as a string inside `ara`.

**Spec:** `docs/superpowers/specs/2026-11-12-ara-3-design.md`. Read it before starting any task. Its "Verified API behaviour" section holds the API facts this plan relies on.

## Global Constraints

- `ara` stays a single executable file with no third-party imports. No build step.
- Object-oriented: one class per responsibility. `OutputHandler` and `AuthenticationProvider` base classes stay.
- Python 3.7 syntax: no walrus operator, no `match`, no `list[str]` generics; use `typing`.
- Version string is `3.0.0`.
- Name is `ARA`, standalone. Descriptor "the role atlas for Azure" and slogan "See who holds the keys." are placeholders; each appears in exactly one constant (`ARAConfig.DESCRIPTOR`, `ARAConfig.SLOGAN`).
- "Azure" is written after the name, never before it.
- Voice in all user-facing text: plain statements and counts. No marketing words.
- Assignment types, exact strings: `Active permanent`, `Active time-bound`, `Eligible permanent`, `Eligible time-bound`, `Active`.
- High-privilege roles, exact strings: `Owner`, `User Access Administrator`, `Role Based Access Control Administrator`.
- API versions: role assignments and role definitions `2022-04-01`; both PIM lists `2020-10-01`; management groups `2020-05-01`; subscriptions `2020-01-01`.
- Exit codes: `0` complete, `1` fatal and nothing written, `2` usage error, `3` incomplete with files written, `130` interrupted with partial files written.
- Tests never touch the network, `az`, or the real `results/` directory.
- After every task: `python3 -m unittest discover -s tests -v` passes and `./ara --help` exits 0. A real scan only has to work from Task 8 on.
- Never log or print a token.
- Model per task is stated in each task heading (Opus 5.5 for new or complex work, Sonnet 5.5 for straightforward work). If a task turns out harder or easier than labelled, stop and check in with Florian.

## Review Focus

Conditions the spec implies that are most likely to hit a real user. Each has a test in the task named.

1. Scope paths differ in letter case between API responses (`resourceGroups` and `resourcegroups`). Rows still group under one scope. Task 3.
2. A role assignment points to a role definition that is not in the role definition list (deleted custom role). The row is kept and shows the role GUID. Task 4.
3. A principal has no display name (`null` or empty) from PIM and Graph. Name filtering does not crash and the report shows the principal ID. Tasks 6 and 9.
4. A complete scan finds zero assignments. ARA writes a valid report and JSON and exits 0. Task 8.
5. The output directory cannot be created or written. ARA prints one error line and exits 1, without a traceback. Task 7.

### Task 4: PIM collection and assignment builder (Opus 5.5)

**Files:**
- Modify: `ara` (replace `PIMClient` 995-1096; new `PIMUnavailable`, `AssignmentBuilder`)
- Test: `tests/test_ara.py`

**Interfaces:**
- Consumes: `AzureAPIClient` (Task 2); `AssignmentCollector.inside`, `Scope` (Tasks 1, 3); `RoleAssignment` (Task 1).
- Produces:
  - `PIMUnavailable(ARAError)`.
  - `PIMCollector(api: AzureAPIClient)`
    - `.eligible(scope: Scope) -> List[Dict]` from `roleEligibilityScheduleInstances`
    - `.active(scope: Scope) -> List[Dict]` from `roleAssignmentScheduleInstances`
    - Both: for a management group, list with `$filter=atScope()` and keep rows at that exact scope; for a subscription, list unfiltered and keep rows inside it. An `APIError` with status 403 is raised as `PIMUnavailable`; other errors pass through.
  - `AssignmentBuilder(role_names: Dict[str, str], subscription_names: Dict[str, str])`; `subscription_names` maps lowercased subscription GUID to display name.
    - `.build(rbac_rows: List[Dict], active_instances: Optional[List[Dict]], eligible_instances: Optional[List[Dict]]) -> List[RoleAssignment]`. `None` means PIM was skipped or unavailable.

Classification rules for `build`:

| Source | Condition | `assignment_type` | start / end |
|---|---|---|---|
| RBAC row | `active_instances` is `None`, or no instance whose `originRoleAssignmentId` equals the row `id` | `Active` | none |
| RBAC row | matching instance has `endDateTime` | `Active time-bound` | from instance |
| RBAC row | matching instance has no `endDateTime` | `Active permanent` | `startDateTime` from instance, end none |
| Eligible instance | has `endDateTime` | `Eligible time-bound` | from instance |
| Eligible instance | no `endDateTime` | `Eligible permanent` | start from instance |

Field rules: `role_id` is the full `roleDefinitionId`. `role_name` is looked up by lowercased trailing GUID in `role_names`, then `expandedProperties.roleDefinition.displayName`, then the GUID itself. `principal_name` is `expandedProperties.principal.displayName` of the instance when present and non-empty, otherwise `None`. `scope_name`, `scope_type`, `resource_type` come from `Scope.from_path`; a subscription scope uses its display name from `subscription_names` when known. Eligible rows are never dropped or merged against active rows. A row whose scope `Scope.from_path` rejects is skipped.
