# ARA 3.0 design: trustworthy scan and HTML report

Date: 2026-11-12
Status: draft, awaiting approval

## Intent

ARA is used by our engineers to see quickly who has which role in an Azure environment. The goal is to widen that: anyone with read access to an Azure environment should be able to run ARA and understand who holds access, without reading CSV.

A code review of 2.1.0 found that exports can silently lose rows and still report success. An attractive report on incomplete data would be worse than the current CSV, so 3.0 fixes the scan first and then adds the report.

This document covers stages 1 and 2 of a longer path:

1. Trustworthy scanner (this document)
2. Single-file HTML report (this document)
3. Download-and-run binaries with built-in login (later, separate design)
4. Hosted product (later, separate decision)

## Goals

- A scan either returns every direct role assignment in scope, or says clearly that it did not.
- Every scan writes a self-contained HTML report that a non-engineer can open and use.
- ARA stays one file, Python standard library only, no build step.
- Less code than today where the review found dead or duplicated parts.

## Non-goals

- Stages 3 and 4: packaging, built-in browser login, hosting.
- Sovereign clouds, classic administrators, deny assignments, Entra directory roles.
- Expanding group membership into effective access.
- Parallel API calls.
- Sortable columns and keyboard row navigation in the report (considered, not chosen).

## Anti-goals

- A report that looks complete when the scan was not.
- A report that makes network requests or needs anything besides the one file.
- Overwriting the last good output with an empty or failed scan.

## Constraints

- Breaking release: 3.0.0. Output fields, CSV columns, exit codes, flags and file location may change.
- Zero dependencies, single executable file `ara`, Python 3.7+.
- Object-oriented structure, as today: one class per responsibility (API client, each collector, PIM merge, name resolver, each output handler, the application). Florian asked for this explicitly. The `OutputHandler` and `AuthenticationProvider` base classes stay, since each has several implementations; the HTML report is a new `OutputHandler`.
- Name: **ARA**, standalone, no expansion. Descriptor and slogan are placeholders and will be revised: "the role atlas for Azure" and "See who holds the keys." The README notes once that ARA began as the Azure Role Assignment Exporter. "Azure" is always written after the name, never before it.
- Voice in report, help text and README: plain statements and counts, no marketing words.

## Approaches

### Scan

1. **Patch in place.** Keep one call per scope; add pagination and `$filter=atScope()` to the five list calls. Smallest change. Stays slow at resource depth and never sees child resources (subnets, SQL databases).
2. **One list per subscription (chosen).** One paginated role assignment list per subscription, grouped by `properties.scope`; `--depth` becomes a filter on the result. Far fewer calls, sees child resources, removes two client classes. Depends on API behaviour that is not yet confirmed (see Assumptions).
3. **Azure Resource Graph.** One query across subscriptions. Dropped: coverage of PIM eligibility is uncertain, so a second path would be needed anyway.

Florian chose 2.

### Report

a. **Template inside `ara` (chosen).** HTML, CSS and plain JavaScript as one string in the script, scan data embedded as JSON.
b. **Separate template file.** Easier to edit; ARA stops being a single file.
c. **Framework with a build step.** Dropped: breaks zero-dependency.

Florian chose a.

## Assumptions to verify first

None of these could be checked offline. The first implementation task is to verify each with one read-only call against the test tenant (Florian logs in with `az login`). Each has a fallback, so the design holds either way.

| # | Assumption | If false |
|---|---|---|
| A | `GET /subscriptions/{id}/providers/Microsoft.Authorization/roleAssignments` without a filter returns assignments at every scope inside the subscription, plus inherited ones from above. | Fall back to approach 1 for role assignments. |
| B | `roleEligibilityScheduleInstances` and `roleAssignmentScheduleInstances` listed at subscription scope without `atScope()` also return instances on resource groups and resources below it. | List PIM per management group, subscription and resource group with `atScope()`, as today. |
| C | An active schedule instance carries `properties.originRoleAssignmentId` matching the `id` of the RBAC role assignment. | Match on (principal id, trailing GUID of role definition id, lowercased scope). |

Record the result of each check in the implementation plan before building on it.

The checks are read-only and run by Claude through Florian's `az` login on the test tenant. They need fixtures in that tenant: a role assignment on a child resource (A), an eligible assignment on a resource group or resource (B), and one currently activated plus one permanent assignment (C). Whether these exist or get created is open (see Open). An assumption that cannot be checked is treated as false.

Two consequences, both my calls:

- For C the merge always does both: join on `originRoleAssignmentId` when present, otherwise on (principal id, role GUID, lowercased scope). It then works whichever way C turns out.
- If A is false, the per-scope clients and `--max-resources` stay.

## Design

### Scan

**Scope input.** One pure function `normalize_scope(text) -> (path, kind)` replaces the current parsing. It accepts the six documented forms, case-insensitively, ignores a trailing slash, and rejects anything else (including resource group paths) with a message listing the valid forms. A bare GUID is tried as a subscription; on 404 it is tried as a management group.

**Depth.** The argparse default becomes `None` and is resolved per scope kind.

| Scope kind | Allowed depths | Default |
|---|---|---|
| Management group | `management-groups`, `subscriptions`, `resource-groups`, `resources` | `management-groups` |
| Subscription | `subscriptions` (the subscription only), `resource-groups`, `resources` | `resource-groups` |

An invalid combination is a usage error, never silently changed.

**Collection.**

- Management groups: one hierarchy call with `$expand=children&$recurse=true`, then one `atScope()` role assignment list per management group.
- Subscriptions: one unfiltered, paginated role assignment list per subscription. Keep rows whose `properties.scope` lies inside that subscription; group by scope. Rows whose scope lies above the subscription are inherited and are dropped here (the management group calls cover them when in scope).
- Depth is applied to the grouped rows: `subscriptions` keeps subscription-level rows, `resource-groups` adds resource groups, `resources` adds everything below, child resources included.
- `--resource-types` filters resource rows by the type parsed from the scope path, case-insensitively. It is a usage error at other depths.
- Scope name, scope type and resource type are parsed from the scope path. Subscription display names come from the subscriptions list.
- Role names: one paginated `roleDefinitions` list per subscription and per management group, keyed by the lowercased trailing GUID.

**Pagination.** One helper in the API client follows `nextLink` until absent. Every list call uses it. No list call reads `value` directly.

**PIM.** Collected with the same per-subscription pattern (assumption B), plus `atScope()` per management group.

- RBAC rows are the base set of active assignments.
- An active schedule instance is joined to its RBAC row through `originRoleAssignmentId` (assumption C) and contributes start and end time. With an end time the row is `Active time-bound`, otherwise `Active permanent`.
- Eligible instances are separate rows, `Eligible time-bound` or `Eligible permanent`. They are never deduplicated against active rows. A principal who is eligible and currently activated shows both rows.
- An active row with no matching schedule instance gets the assignment type `Active`, because its duration is unknown. This covers `--skip-pim`, a 403 on PIM, and rows PIM does not report. `Active` is a fifth value. (My call: labelling them "permanent" would be a false statement.)
- PIM availability is tracked per subscription and management group. Metadata `pim` is `included`, `partial`, `skipped` or `unavailable`, and `pim_unavailable_scopes` lists where it was refused. The first 403 logs one warning.
- A 403 on PIM is a missing permission, not a failure: exit code 0, with the banner. Any other PIM error that survives the retries makes that scope a failed scope. (My call.)

**Principal names.** Resolved once after the scan with `POST /directoryObjects/getByIds`, 1000 ids per call.

- Graph token: from `az`, or from the new `AZURE_GRAPH_TOKEN` environment variable.
- A principal Graph does not return gets the name `Unknown`. That means "not found in the directory": deleted, or not visible to the person running the scan (a guest, or a principal from another tenant). The report says exactly that and never calls it "deleted". (My call, after the reviewer pointed out `getByIds` also omits objects the caller cannot read.)
- `--principal-name-filter` and `--exclude-managed-identities` need Graph. When either is set, ARA checks before scanning that it has a working Graph token and exits with code 1 if not. If name resolution fails after the scan, the output is written unfiltered and marked incomplete.
- Without a Graph token, or when Graph fails, names are `null`, metadata records `names: unavailable`, one warning is logged, and the report shows the principal ID instead. `Unknown` is never used for "could not ask".
- Service principals with `servicePrincipalType` `ManagedIdentity` get principal type `ManagedIdentity`. `--exclude-system` is replaced by `--exclude-managed-identities`, which filters on that. (My call: the old flag matched a name prefix that real identities do not have.)

**Errors and exit codes.**

- Retry on 429, 5xx, connection errors and timeouts: up to 4 attempts, waiting `Retry-After` when present, otherwise 2, 4, 8 seconds.
- On 401 with the `az` provider, fetch a new token once and repeat the call. With a static token, stop the scan.
- A scope that still fails is recorded with its error; the scan continues.
- If the root scope cannot be read, ARA exits without writing any file.
- On Ctrl-C or a stopped scan, ARA writes what it has, marked incomplete.
- Incomplete output goes to `role_assignments_<scope>.partial.html` and `.partial.json` (and `.partial.csv`), so it never replaces a complete result. Complete output is written to a temporary file and renamed. A complete scan with zero rows is a valid result and is written normally. (My call.)

| Exit code | Meaning |
|---|---|
| 0 | Complete |
| 1 | Fatal: nothing written |
| 2 | Usage error (argparse) |
| 3 | Incomplete: files written, at least one scope failed or the scan was stopped |
| 130 | Interrupted, partial files written |

**Authentication.** Order: `--token`, environment variables, `az`, interactive prompt. The prompt only appears when stdin is a terminal. The keychain provider is removed. `az` is located with `shutil.which` so it also resolves on Windows.

**Output location.** `./results/` in the working directory, or `--output-dir`. Directory creation errors are reported as a normal error.

**Removed flags.** `--max-resources` (no per-resource calls remain) and `--exclude-system`. `--api-delay` stays.

**Filter validation.** `--assignment-type-filter` and `--principal-type-filter` values are checked against the known values; an unknown value is a usage error.

### Output

Every scan writes `role_assignments_<scope>.html` and `role_assignments_<scope>.json`. `--format csv` additionally writes the CSV. `--format` no longer selects between JSON and CSV. The scope part of the file name is reduced to letters, digits, `-` and `_`.

**JSON metadata.**

```json
{
  "metadata": {
    "tool": "ARA",
    "version": "3.0.0",
    "schema_version": 3,
    "scan_timestamp": "2026-11-12T08:14:00Z",
    "scope": "/providers/Microsoft.Management/managementGroups/my-mg",
    "depth": "resource-groups",
    "complete": true,
    "failed_scopes": [],
    "pim": "included",
    "pim_unavailable_scopes": [],
    "names": "resolved",
    "filters_applied": {},
    "management_groups_scanned": 2,
    "subscriptions_scanned": 5,
    "scopes_with_assignments": 15,
    "total_assignments_found": 42
  },
  "role_assignments": []
}
```

- `pim`: `included`, `partial`, `skipped` or `unavailable`. `names`: `resolved` or `unavailable`.
- `total_scopes_scanned` and the top-level `scopes_scanned` list are removed: ARA no longer visits each resource group or resource. The three counts above replace them. The report heading shows management groups and subscriptions scanned, which is the true coverage. (My call.)
- `failed_scopes`: list of `{"scope": "...", "error": "..."}`.
- `scan_timestamp` is UTC.
- Assignment rows keep the 2.x field names. `principal_name` may be `null`. `assignment_type` may be `Active`.

**CSV.** Fixed columns in this order: Name, Principal ID, Type, Role, Scope, Scope Path, Scope Type, Assignment Type, Resource Type, Start Date, End Date. A cell starting with `=`, `+`, `-` or `@` is prefixed with a single quote.

**Console summary.** Kept, shortened, and ends with the path of the report. It states PIM status and the number of failed scopes.

### HTML report

One self-contained file. It follows mockup direction A, kept at `.superpowers/brainstorm/92879-1794475906/content/report-directions.html` (view A): light paper ground, ink text, one teal accent, red only for risk.

**Layout, top to bottom.**

1. Heading with scope, scan time, management groups and subscriptions scanned, and completeness.
2. A banner when the scan is incomplete, PIM was unavailable or skipped, or names were not resolved. It says what is missing in one sentence each.
3. Four figures: direct assignments; high-privilege assignments; eligible through PIM; principals not found in the directory.
4. Search field and filter chips: High privilege, Eligible, Users only.
5. Count line ("12 of 148 assignments").
6. Table: Principal (name, type), Role, Scope (name, type), Assignment, Ends.
7. A side panel that opens on row click.

**High privilege** means the roles Owner, User Access Administrator and Role Based Access Control Administrator. The list is one constant.

**Drill-down.** Clicking a principal opens a panel listing every assignment of that principal. Clicking a scope opens the same panel listing everyone assigned on that scope. Esc and a close button close it.

**Chosen extras.**

- Shareable views: search text, active chips and the open panel are stored in the URL fragment and restored on load.
- Export what you see: a button downloads the currently filtered rows as CSV, with the same columns and escaping as the CSV file. Principal ID and scope path each have a copy button.
- Themes and print: follows the system light or dark setting, with a toggle; a print stylesheet prints the table without controls.

**Rules for the builder.**

- Scan data is embedded as JSON in a `<script type="application/json">` element with `<` escaped. All tenant-supplied text (display names, scope names, role names) is inserted with `textContent`, never as HTML. Display names are attacker-controllable: anyone who can register an app picks one.
- No network requests: system font stack, no external scripts, styles, fonts or images. A Content-Security-Policy meta tag enforces it.
- The report stays usable with 20,000 rows. How (paging, incremental rendering) is the builder's choice.
- The theme toggle may use `localStorage`; the report must work when storage is blocked.
- Controls are at least 44px tall, focus is visible, and motion is disabled under `prefers-reduced-motion`.
- No violet. No animation on scroll.

### Code removed

Keychain provider and its save prompt; both `lru_cache` layers; `Scope.from_path`; `RoleAssignment.full_scope_path`; `MAX_CONCURRENT_REQUESTS`; `ScanResult.organization`; `safe_print`, the `SIGPIPE` line and the `BrokenPipeError` handler; unused imports; `ResourceGroupClient` and `ResourceClient` (if assumption A holds); the three near-identical blocks in `_scan_scope_assignments`, replaced by one function that builds a `RoleAssignment` from API properties.

### Tests

One file, `tests/test_ara.py`, standard library `unittest`, no network. It loads `ara` by path. It covers:

1. `normalize_scope`: the six documented forms, mixed case, trailing slash, a resource group path, a bare GUID.
2. PIM merge and classification: eligible plus activated gives two rows; permanent and time-bound; PIM skipped gives `Active`.
3. Filter matching: each filter, combinations, invalid values rejected.
4. Pagination helper with a fake two-page response.
5. Grouping a subscription-wide list by scope and applying each depth.
6. CSV rows: fixed columns and formula escaping.
7. Report data embedding: a display name containing `</script>` and one containing `<img onerror>` do not break out.

### Documentation

README rewritten for 3.0: name and descriptor, report first, corrected defaults, exit codes, the new flags, removed flags, no benchmark table, no `PERFORMANCE.md` link, no Black badge. CHANGELOG gets a 3.0.0 entry listing every breaking change. `.gitignore` gains `results/*.html` and `.superpowers/`.
